# RAG Lab — 設計書

> 3年前に構築した社内文書RAGチャットボット（LangChain 0.0.x + Pinecone + Slack Bot + AWS Lambda）を、
> 2026年時点のアーキテクチャで再設計したもの。学習・ポートフォリオ目的で自作する前提で構成を選定している。

## 1. 背景と目的

- **旧版**: 社内の設計書・業務マニュアル・運用手順書を対象に、自然言語で質問すると根拠資料付きで回答するRAG。
  LangChainのChain群、Pinecone、LayoutParser + GPT-4o Visionによる図表文章化、自作の3段評価スクリプトで構成。
- **v2の狙い**: 「自作しても学びの薄い部分（ベクトルDBの運用、モデルのホスティング）はマネージドに逃がし、
  理解したい部分（チャンク戦略・ハイブリッド検索・リランク・評価）は自分の手で握る」構成に作り直す。

## 2. 要件

| 項目 | 内容 |
|---|---|
| 利用者 | 社内 約10名 |
| リージョン | `ap-northeast-1`（東京）固定。文書データを東京リージョン外に出さない |
| 認証 | アプリ内ログインなし。ネットワーク層（Tailscale）でアクセス制御 |
| セキュリティ | 文書データがAWSリージョン外に出ないこと（LLM APIへ送信する検索チャンクを除く） |
| 対象文書 | PDF / docx / xlsx（図表を含む） |
| IaC | Terraform 100%。手作業構築なし |
| コスト運用 | `terraform destroy` で一発撤去できること。夜間・週末は停止できること |
| 開発体制 | 1人・片手間 |

## 3. アーキテクチャ選定

### 3.1 選定の軸

RAG構成の選定は実質4軸で決まる。本プロジェクトの立ち位置は以下。

| 軸 | 問い | 本プロジェクト |
|---|---|---|
| データ所在 | 文書を外部SaaSに出せるか / リージョン縛りは | 東京リージョン内に閉じたい |
| 運用工数 | 誰が面倒を見るか | 1人・片手間 |
| 検索品質の握り | チャンク戦略・ハイブリッド検索・リランクを自分でチューニングしたいか | **したい（学習目的）** |
| 目的 | 速く動かすか、理解するか | **理解すること** |

### 3.2 選択肢の比較と結論

| 選択肢 | 内容 | 判定 |
|---|---|---|
| 全マネージド (Bedrock Knowledge Bases) | 取り込み〜検索まで全部AWS任せ | ✗ 中身がブラックボックスで学習目的と相反 |
| **セミマネージド (本採用)** | 検索・取り込み・評価は自作、DBとLLMはマネージド | ✓ 理解したい部分だけ自作できる |
| フルスクラッチ | 埋め込みモデルも自前ホスト | ✗ 10人規模では過剰、GPUコストの無駄 |

**結論**: 「理解したい部分だけ自作し、理解しても得るものが少ない部分はマネージドに逃がす」= セミマネージド構成。

### 3.3 アーキテクチャスタイル: モジュラーモノリス

本システムは **モジュラーモノリス + マネージドサービス** に分類される。

- アプリ本体（Next.js + FastAPI）は **1デプロイ単位・1リポジトリ**（1 Fargate タスクに2コンテナ。3.4参照）。
- DBも **1つのPostgres** に集約（ベクトル / 全文検索 / 会話履歴 / メタデータ）。
- 取り込みバッチは別プロセスで起動するが、**コードベースは同一**。マイクロサービスではない。

**なぜマイクロサービスにしないか**: チーム分割・独立スケール・障害隔離という分割の動機が10人規模では一つも存在しない。
分割はコストだけ払って利益ゼロになるため、あえてモジュラーモノリスを選ぶ。モジュール境界（ingest / retrieval / chat / eval）は
コード内のパッケージ分割で表現する。

### 3.4 デプロイ構成: Next.js と FastAPI を同一 Fargate タスクに置く（ADR）

**決定**: フロント(Next.js)とバックエンド(FastAPI)を **1 Fargate タスクの2コンテナ** として同居させる。
CloudFront + S3 による静的配信への分離は **採用しない**。

```
Fargate task
 ├─ frontend コンテナ (Next.js, :3000) ── localhost:8000 へプロキシ
 └─ backend  コンテナ (FastAPI, :8000)
```

**前提**: 現行フロントは静的サイトではない。App Router の `next start`（Nodeサーバ）と
`next.config` の rewrites プロキシ（CORS回避）がサーバ側で動くため、S3+CloudFront に載せるには
静的化（SSR・プロキシの放棄）が必要 = 構成の作り直しになる。

**選定理由（同一タスク・2コンテナ）**
- **ローカル再現性**: docker compose も別イメージ・別サービス構成。タスク内2コンテナなら `BACKEND_URL` が
  `localhost:8000` になるだけで、ローカルの構成がそのまま dev に写る。
- **モジュラーモノリスと一致**: デプロイ単位は1つ（1タスク）に保ちつつ、コンテナ＝モジュール境界は分ける。
- **10人規模では十分**: 別々の Fargate サービスに割る動機（独立スケール・独立デプロイ）が存在しない。
  コストだけ増えて利益ゼロ。
- **コスト**: 常時起動タスクが1つで済む。

**選定理由（CloudFront を使わない）**
- **閉域前提と矛盾**: 利用者10人が Tailscale 経由でアクセスする閉じたシステムに、公開CDNの CloudFront を
  挟むと公開面（攻撃対象）が増える。CloudFront は公開・地理分散・高トラフィック静的配信のための道具で、方向が逆。
- **配信最適化が不要**: 利用者10人・同一組織ではエッジキャッシュ・広域低遅延の価値が出ない。
- **身軽さの維持**: 部品が増えず、`terraform destroy` 一発の撤去性を保てる。

**見直しトリガー**: 社外公開する／利用者が数百〜数千規模になる／フロントを完全静的化できる、のいずれか。
その時は S3+CloudFront(静的) + Fargate(API) への分離を再検討する。

## 4. 全体構成

```
                    ┌─ Tailscale VPN ─┐
  社内ユーザー ──────┤                 │
                    └────────┬────────┘
                             ▼
┌─ VPC (10.0.0.0/16) ap-northeast-1 ───────────────────┐
│                                                       │
│  ┌─ public subnet ────────────────────────────┐       │
│  │  ECS Fargate (1タスク)                      │       │
│  │  ┌──────────────┬──────────────────┐       │       │
│  │  │ Next.js (UI) │ FastAPI (RAG API)│       │       │
│  │  └──────────────┴────────┬─────────┘       │       │
│  └───────────────────────────┼────────────────┘       │
│                              │                        │
│  ┌─ private subnet ──────────▼────────────────┐       │
│  │  RDS PostgreSQL 16 + pgvector              │       │
│  │  （ベクトル / 全文索引 / 会話履歴 / メタデータ）│       │
│  └────────────────────────────────────────────┘       │
│                                                       │
│  S3（原本文書）──► ECSタスク(取り込みバッチ)──► RDS      │
└───────────────────────────────────────────────────────┘
                              │
                              ▼ (HTTPS)
                    LLM API（生成・埋め込み・PDF読解・リランク）
```

### 設計判断

- **ALB・NAT Gatewayなし**: この2つで月$55かかる。Fargateをpublic subnetに置き、Security Groupで
  Tailscaleサブネットルーター経由以外を遮断。10人規模ではこれで十分かつ月額が半減する。
- **DBは1つに集約**: ベクトル・BM25全文検索（`pg_trgm` / `tsvector`）・会話履歴・文書メタデータを全部Postgresへ。
  旧版で未完だった「DynamoDB移行」の動機自体を設計で消す。

## 5. データフロー

### 5.1 取り込み（バッチ）

1. S3に文書アップロード → EventBridgeで取り込みECSタスク起動。
2. PDFをページ画像化し、マルチモーダルLLMで構造化テキスト化（図表もここで文章になる。旧LayoutParser工程の置き換え）。
3. チャンク分割: 大きめ（1,500〜2,000字、オーバーラップ200）+ 各チャンクに「文書タイトル・章の要約」を前置き（contextual retrieval）。
4. 埋め込みAPIでベクトル化 → pgvectorへUPSERT。文書ハッシュで差分検知し、再取り込みは変更分のみ。

### 5.2 検索・回答（オンライン）

1. 質問をベクトル検索（top 20）+ 全文検索（top 20）→ RRF（Reciprocal Rank Fusion）で統合。
2. LLMで候補をリランク → 上位5チャンクで回答生成（ストリーミング）。
3. 根拠文書のS3署名付きURLを回答に添付（原本をその場で開ける。旧版になかった改善）。

> **自作する範囲（学習の核）**: チャンク戦略、ハイブリッド検索（ベクトル + BM25 + RRF）、LLMリランク、評価。
> このパイプラインはLangChainのChainに任せず、SDK直叩きで組む。

## 6. Terraform構成

```
terraform/
├── environments/
│   └── prod/
│       ├── main.tf          # モジュール呼び出しのみ
│       ├── backend.tf       # S3 + DynamoDB state lock
│       ├── providers.tf     # region = ap-northeast-1 固定
│       └── terraform.tfvars
└── modules/
    ├── network/    # VPC, subnet, SG, Tailscaleサブネットルーター用EC2 (t4g.nano)
    ├── database/   # RDS PostgreSQL 16 + pgvector, backup 7日
    ├── app/        # ECS cluster, Fargate service, ECR, task定義
    ├── ingest/     # S3, EventBridge, 取り込み用ECS task定義
    └── secrets/    # Secrets Manager (LLM APIキー, DB認証情報)
```

### 設計原則

- **environmentsとmodulesを分離**し、moduleは環境非依存に保つ（dev追加が数行で済む）。
- **APIキー・DBパスワードはSecrets Manager経由でタスクへ注入**。tfvarsにもコードにも平文で書かない
  （旧版のbuildspec.ymlにDocker Hubパスワードを平文で書いていた反省を回収）。
- stateはS3バックエンド + DynamoDBロック。ローカルstate禁止。

### コスト運用（destroy可能・停止可能）

- `terraform destroy` が一発で通ること: S3は `force_destroy = true`、RDSは `skip_final_snapshot = true`。
  文書はS3原本から再取り込みできるため、DBは消えても復元可能な設計。
- 夜間・週末停止: EventBridge SchedulerでFargateの `desired_count` を0に、RDSを stop。月額をさらに半減できる。

## 7. 概算コスト（月額）

| リソース | 概算 |
|---|---|
| Fargate 0.5vCPU/1GB 常時1タスク | ~$18 |

## 8. 技術スタック

| レイヤ | 採用 | 旧版から | 理由 |
|---|---|---|---|
| フロント | Next.js + Vercel AI SDK | Chatbot UIフォーク | ストリーミング・ツール表示が数十行で済む |
| バックエンド | FastAPI（LLM SDK直叩き） | LangChain Chain群 | Chainのブラックボックスを外し、検索処理を自分で握る |
| ベクトルDB | PostgreSQL + pgvector | Pinecone | 会話履歴・メタと同居。データが東京リージョン内に閉じる |
| 図表処理 | マルチモーダルLLMのPDFネイティブ入力 | LayoutParser + GPT-4o Vision | モデル標準機能になったため自作工程を廃止 |
| 評価 | Ragas / promptfoo | 自作3段スクリプト | 「質問自動生成→採点→CSV」が標準機能化 |
| IaC | Terraform | Serverless Framework + 手作業 | 全リソースをコード化、destroy可能に |
